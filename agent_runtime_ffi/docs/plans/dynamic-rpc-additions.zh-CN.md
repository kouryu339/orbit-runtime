# RPC 工具集动态新增计划

状态：外部 gRPC 动态新增已实现，专项、回归和真实 DLL 闭环验证通过。2026-10-29。

基线：main / v0.5.2，`b8d3344`。
工作分支：`jiangrong/dynamic-rpc-additions`。

## 1. 目标和边界

Runtime 启动后，宿主可以连接一个新的 RPC 服务，把其完整工具集一次性新增到当前 Runtime。
只新增，不修改任何已经接受的端点或工具；已有会话、审批、Workflow 执行继续沿用原契约。

| 操作 | 计划行为 |
| --- | --- |
| 新端点 ID，发现的全部工具名也全新 | 校验通过后整体登记 |
| 已存在端点 ID，包括相同配置的重复请求 | 拒绝，不解释为更新或刷新 |
| 新端点中含任意已存在工具名 | 整个请求拒绝，不只跳过重名项 |
| 与内置工具、已有动态工具、工作流引用名称冲突 | 整个请求拒绝 |
| 原端点增加、删除或修改工具后要求重新发现 | 不开放 |
| 修改地址、超时、协议、输出裁剪或启动配置 | 不开放 |
| 删除、断开已登记端点或覆盖原工具 | 不开放 |
| 已登记服务断开后恢复到原地址 | 后续调用按原配置连接，不刷新目录、不重放失败调用 |

新增不需要等待原会话关闭，因为没有替换其依赖。但新增不等于授权：Role／Feature 工具范围、
权限准入、用户审批保持原规则；不得把新工具自动加入所有 Agent 的活动工具列表。
需要配置新职责时，沿用已有集群和 Skill 事务接口及其占用限制。

不允许用新 ID 绕过旧工具名冲突；保留 `WorkflowRef_` 等内部命名空间，禁止 RPC 占用。
相同地址并不证明相同服务身份；仍以登记 ID、完整工具目录及工具名冲突检查为准。

## 2. 基线代码的问题

以下记录实现前的基线；本分支已按第 4 节收口 RPC 目录和消费入口。

- `runtime.rs::register_resources_with_base` 在启动后拒绝资源登记；不能放开整个 resources 注册来实现新增 RPC。
- `runtime/rpc.rs::install_rpc_tools_from_config` 在启动时做 ListTools、契约校验、执行器安装和 AI 元数据登记。
  这段代码逐个发布工具，后面的工具失败时，之前写入的全局条目可能已经可见，不能直接复用为动态事务。
- `corework/src/rpc_tool.rs` 的端点／工具表只提供 insert/get；同名 insert 拒绝。
  但 `SystemRegistry::register_dynamic_with_metadata` 和 `ai-assistant/src/runtime_tools.rs` 会覆盖同名值。
  仅在 FFI 入口判断重复不足以建立原子、不覆盖的约束。
- Framework 的 SystemRegistry 和 AI RuntimeTool 元数据目前是进程级全局；多个 Runtime 句柄不能靠各自 Vec 的检查避免相互覆盖。
- 宿主查询和 Workflow 编译读取 `RuntimeFacade.runtime_tools`；普通会话在创建时获得一个
  `WorkflowRuntimeToolCatalog::new(self.runtime_tools.clone())` 副本。
  仅修改 Facade 列表会导致旧会话里的 AI Workflow 工具看不到新增节点。
- 原生 FC 在构建模型请求时读取活动工具对应的元数据；工具说明、参数校验、实际执行也有各自读取入口。
  这些读取必须与工作流编译使用同一个目录来源。
- `agent_runtime_invoke_v1` 当前持有 Facade 写锁调用命令。直接在里面等待 ListTools，
  会阻塞该句柄上的发送、暂停、关闭等宿主操作，不能让网络等待占住整个句柄写锁。
- gRPC 与 JSON-lines 调用当前都按请求建立连接。连接池、健康守护和自动重启不是动态新增的前提。

## 3. 对外接口草案

只新增一个命令：`runtime.add_rpc_endpoint`。继续使用现有通用 invoke ABI，无需增加 C 导出函数。
这是宿主管理接口，不默认作为 AI 工具开放。

```json
{
  "schema": "agent-runtime-rpc-endpoint-add/v1",
  "endpoint": {
    "id": "project_tools",
    "protocol": "grpc",
    "endpoint": "http://127.0.0.1:55061",
    "timeout_ms": 30000,
    "to_ai_max_chars": 12000
  }
}
```

端点字段沿用 ResourceRpcEndpointConfig 的命名和默认值，避免产生第三套配置字段。
不接受内联工具描述，工具定义来自服务的 ListTools；不接受 update/replace/upsert 标志或未知字段。

返回内容：新增端点摘要、工具名称、工具数、目录 revision、契约摘要哈希。
配置存储中的地址、密钥、环境变量不进入公共事件和通用目录查询。
沿用 `runtime.get_rpc_endpoint_definitions`、`runtime.get_tool_definitions`、
`runtime.get_workflow_node_definitions`，增加可选目录 revision；不另造列表接口。

已采用错误：`rpc_endpoint_exists`、`rpc_tool_name_conflict`、`invalid_argument`、
`rpc_failed`、`bad_state`。冲突返回全部冲突名称；发现／校验失败不产生部分成功。

目录 revision 只用于标记结果与缓存。纯新增不要求 expected_revision：准备期间出现其他互不冲突的新增，
提交时基于最新目录重新检查并合并；同一名称的竞争只允许一个成功。
重复请求明确拒绝，宿主对响应丢失可查询端点目录确认，不能通过重复提交更新配置。

## 4. 最小可靠架构

### Runtime 自己持有动态目录

引入每个 Runtime 一份的共享 RPC 目录，包含端点、不可变工具元数据、执行器和 revision。
启动登记和动态新增都走同一套准备／提交逻辑。每次提交发布一个完整、不可变的新快照。
准备阶段不能写入任何执行器表或 AI 元数据表。

内置静态工具保持共享、只读。RPC 通过 Runtime 所属的目录和执行上下文解析；
不能继续依靠进程级动态表或在找不到实例条目时回落到其他实例的全局 RPC 条目。
同一 Runtime 内工具名唯一，不同 Runtime 可以登记同名工具到不同服务并独立执行、销毁。

这会涉及工具解析入口的有限调整，不改变 Agent 状态机、Workflow 连线编译算法或节点执行算法。
不重写全局 World／事件总线；只收口 RPC 工具目录的所有权和读取路径。
如果执行路径仍依赖全局动态表，则该阶段尚未完成，不能宣称支持安全动态新增。

### 一次请求，内部两段执行

1. 在短锁内检查 Runtime 状态，取得当前目录与候选配置，建立受生命周期保护的调用。
2. 释放 Facade 写锁，连接候选服务，获取完整 ListTools，并校验协议、名称、参数、类型、能力与大小限制。
3. 构造候选端点和执行器，不向活动目录发布。若支持托管进程，候选进程也归准备对象独占。
4. 重新进入提交锁，检查 Runtime 未关闭／切换生命周期，并针对最新快照检查所有冲突。
5. 一次性发布整个目录、revision 及可查询配置。读者只能看到旧快照或新快照，不能看到半套工具。
6. 提交后发出一个变更事件，结果携带 revision；事件用于刷新，不作为事实来源。

准备失败或竞争失败丢弃候选；已存在的注册、连接和执行全部保留。
关闭与准备并发时必须取消或拒绝提交，不能在句柄关闭后登记；不得延长原有句柄锁到网络等待阶段。
发现需要总截止时间和目录数量／响应体大小上限，不能只给每次重试一个新超时。

### 消费方一致

- 工具说明、原生 FC 参数定义、参数校验、审批安全元数据和执行分派读取同一实例目录。
- 一次模型请求固定所用工具定义；新增不改变原工具元数据，也不改变已发请求或待审批调用。
- 普通会话的 WorkflowRuntimeToolCatalog 改为共享目录读取，不能继续持有启动时 Vec 副本。
- 宿主和 AI 的 Workflow 验证／登记都读取一次目录快照；旧工作流不重编译，运行图和引用快照保持稳定。
- 工具目录、Workflow 节点目录和端点查询都能在提交后看到新增项；Activity/Skill 授权继续单独过滤。
- 两个已弃用 Studio 页面不恢复、不扩展。

### 持久化与恢复

第一阶段新增接口不读写宿主配置文件；宿主保存成功的端点配置，在重启后重新登记。
不增加文件监视器，不依赖外部文件操作工具。

若重启时已有正式 Workflow 引用动态新增工具，宿主必须在 Runtime.start 前把这些端点放回
resources 注册，使启动按原顺序先发现工具、再恢复 Workflow；不能承诺先启动再补工具就能恢复所有资源。
历史会话恢复也必须先具备其工具依赖和授权。完整工具契约版本固定属于恢复验证的后续加强项，
现有代码没有提供远端服务版本不变的保证，不应在新接口中宣称已经做到。

## 5. 实施顺序

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| A：目录基础 | 分离 prepare/commit、禁止覆盖、Runtime 所属目录与读取入口、启动共用新路径 | 多句柄隔离、完整目录原子可见、启动回归通过 |
| B：新增接口 | 通用 invoke 命令、外部 gRPC 服务发现、锁外准备、冲突拒绝、查询和变更事件 | 活跃会话期间新增成功，原调用及审批不变，宿主和 AI Workflow 均可用 |
| C：SDK 与恢复 | Rust/Python/Go/C++ 方法、capability、重启登记说明、真实 DLL 验证 | 新增→发现→授权后调用→Workflow 编译执行→重启恢复闭环 |
| D：可选扩展 | 新增托管 process 服务，或新增 JSON-lines 检索服务 | 各自补进程清理或检索资源绑定测试后再开放 |

第一批只承诺外部 gRPC 业务工具服务。不是放开 resources 整体修改；JSON-lines 的 RAG 绑定、
进程启动权限和异常退出治理不混入第一批。连接池可独立优化，保持现有每次调用连接即可完成新增闭环。

## 6. 必需验证

- 新端点可用；发现超时、空／重复／非法目录、参数契约错误时目录和 revision 完全不变。
- 已有端点同 ID（无论配置是否相同）、与内置或 WorkflowRef 名称冲突，全部拒绝且旧执行器未被替换。
- 多工具目录最后一项失败时，前面的工具也不能被查询或执行。
- 并发相同 ID／同名工具只能一个成功；无冲突新增可全部成功，revision 不丢失。
- 阻塞 ListTools 时仍能暂停／关闭已有会话；关闭 Runtime 后候选不能提交。
- 模型请求中、等待输入、暂停、待审批及 Workflow 执行期间新增：原调用契约与权限均不变。
- 已存在普通 AI 会话经合法授权后能使用新工具；其 Workflow 校验／编译同样能识别新增节点。
- 两个 Runtime 使用同名工具连接不同服务，不串元数据、执行器或目录；关闭一个不破坏另一个。
- 不获得授权的 Agent 不因新增而看到／调用新工具；保留已有审批流程。
- 宿主保存成功配置并在重启 start 前重新登记后，Workflow 恢复和执行通过。
- 服务断开／恢复遵守原调用失败语义，不刷新旧目录，不自动重放有副作用请求。
- 新事件不包含敏感连接字段；revision、契约哈希和错误可定位。

## Engineering Review

Architecture: 仅追加不可变 RPC 注册；统一实例目录，复用现有发现与执行协议，不改变 Workflow 核心算法。

Code: 一个宿主新增命令；复用现有三个查询，避免刷新、修改、移除和连接池进入本轮范围。

Concurrency: 锁外发现、锁内重验与一次发布；存活会话可继续运行，不允许替换其工具。

Resource: 有界发现超时和目录大小；首期不新增文件 IO、常驻监视器或进程监督任务。

Audit: 目录 revision、不可变契约摘要、一个新增事件，公共字段脱敏。

Verification: 新增 5 项真实 gRPC 专项测试，包含在 157 项 FFI 回归中；
355 项 AI 模块测试、11 项 Rust SDK 测试全部通过。C++ 头文件语法与 Go 非 cgo 编译通过。
Python SDK 加载新 DLL，验证新增、端点／工具重名拒绝、目录与事件、Workflow 编译执行，
以及宿主在重启前恢复端点配置后再次执行 Workflow。未逐项模拟所有 LLM／待审批状态，
已验证新增不自动授权，现有权限相关回归通过。

Risks: RPC 元数据与执行器已按实例隔离，但原有全局 Workflow 资源所有权仍限制同进程同时启动多个完整 Runtime。
专项验证的是独立 RPC 目录，不宣称完整多 Runtime 并行启动。Runtime 冻结登记无法约束服务端自行修改实现；
重启需要宿主先恢复端点，远端契约版本校验尚需后续加强。

Decisions Needed: 无。本轮保持只新增外部 gRPC；托管进程、动态检索和连接池不纳入。

请求结构见 [JSON Schema](../rpc-endpoint-add.schema.json)。本分支尚未合并或发布。
