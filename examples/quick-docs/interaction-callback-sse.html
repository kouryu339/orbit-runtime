先界定 Callback 的位置

BOUNDARY
  • 本页的 callback 指前端操作处理器与宿主回传逻辑：点击、提交、允许 / 拒绝，再映射成 Runtime command。
  • ABI 1 的 Runtime 事件出口采用 next_event_v1 拉取；C ABI 的能力声明为 callbacks:false。
  • 浏览器 EventSource.onmessage 属于客户端接收回调；SDK EventSink / 订阅属于宿主分发层。
  • 内部状态机和模型流式回调另有用途，与宿主公共事件传输分层。

回传检查：三道门

CHECK BEFORE ACTION
  • 前端：会话已初始化、输入有效、操作没有正在提交；按最新会话状态控制按钮。
  • 宿主：检查登录、租户 / 用户与 conversation 访问范围，验证字段并路由到正确 Runtime。
  • Runtime：检查生命周期、命令 admission 与当前待审批项；以收到命令时的状态为准。
  • UI 状态可能落后于运行时。按钮可点只代表本地判断，最终要处理服务端拒绝或过期响应。

宿主鉴权由集成应用承担。前端检查改善交互，服务端检查保证实际边界。

交互状态：消费会话投影

STATE FOR UI
  • 会话 UI 使用 frontend:state_snapshot；消息增量取 payload.ledger_delta。
  • 主要依据 payload.conversation_state 判断交互：waiting、thinking、executing、compacting、stopping。
  • 当前 Lit 普通发送在 waiting 时开放；运行中显示暂停，压缩和停止阶段保持对应等待状态。
  • agents[].status 用于展示各 Agent 的内部状态，不能代替整个会话的交互状态。

Runtime 的 send_message 支持 thinking / executing 时插入输入；当前 Lit 常规输入框采用更严格的 waiting 交互策略。宿主按产品需求接入。

4

工具审批：按 Call 关联

PERMISSION ROUND TRIP
  • 工具策略按 effect 选择 full / ask / deny。Ask 在实际执行前登记待审批项并等待。
  • pending_permissions 驱动输入框上方审批区；工具气泡维持 waiting_permission 状态。
  • 用户操作回传 conversation_id + tool_call_id + decision，决定为 allow 或 deny。
  • Broker 在互斥锁内取走待审批项；同一 Call 的重复或过期决定返回 resolved:false。
  • 当前审批等待上限为 300 秒；拒绝、超时或取消进入对应工具结果，只有获准后才继续该工具调用。

5

Widget：用户输入的回传

USER INPUT
  • Assistant 独占行中的 input / select / confirm 标签由前端解析成控件。
  • 本轮控件共用一个提交按钮，仅提交已就绪的值，转换为普通用户消息，例如 格式: PDF。
  • 提交走 conversation.send_message；控件标签本身不作为工具调用或参数执行。
  • 新的 user / assistant 消息到来后，旧控件过期；已提交 / 过期控件保留值并停止操作。

Widget confirm 收集用户表达；工具权限审批解除某一次 tool_call 的执行等待。两者使用不同入口与身份。

6

事件：展示、状态与持久化

EVENT SEMANTICS
  • frontend:state_snapshot 提供 UI 投影，含会话状态、待审批、消息增量与临时 assistant_stream。
  • conversation.state_delta 传递计划、焦点、Agent 等状态增量；conversation.ledger_delta 承载持久事实。
  • 正式工具记录以 call_id 合并申请、开始、完成与失败；临时流按 turn / attempt / sequence 替换。
  • 临时流不进入持久历史；最终记录到达后替换占位。LLM usage / error 是 ledger 事实子类型。

SSE：宿主提供的下行通道

HOST TRANSPORT
  • Runtime 事件先进入消费式队列，宿主取出完整 agent-runtime-event/v1 envelope，再编码为 SSE。
  • 每个 Runtime handle 宜由一个消费入口拉取，之后 fan-out 给 UI、存储和其他订阅者；多个直接 pull 会竞争取走事件。
  • SSE 的 id、Last-Event-ID、heartbeat、鉴权、补读与慢客户端处理由宿主实现。
  • Runtime 内的 event_seq / conversation_event_seq 辅助实例内排序；跨进程持久 cursor 由宿主另行管理。

断线与竞态：按事实收敛

RECONCILIATION
  • SSE 断开只说明连接变化；客户端进入 reconnecting，不能据此判断 Agent 停止或工具失败。
  • 宿主需要用事件补读或最新快照对账，覆盖首次快照读取与建立订阅之间的窗口。
  • 按当前实例和会话范围处理事件序号；跨重启重新建立基线，不沿用旧实例的排序假设。
  • 命令响应丢失时先核对状态，尤其是审批与外部副作用；可重连不代表业务动作可以重复执行。

宿主如何接线

CONCEPTUAL / SIMPLIFIED
COMMAND HANDLER + EVENT PUMP示意，省略框架与错误分支
// 上行：用户操作由宿主转成命令
async function onPermissionDecision(user, body) {
  authorizeConversation(user, body.conversation_id);
  validateDecisionFields(body);
  return await runtime.invoke(
    "conversation.resolve_tool_permission", body);
  // resolved:false 表示已没有对应待审批项
}

// 下行：一个消费入口，分发给多个订阅者
while (hostRunning) {
  next = runtime.next_event(pollTimeout);
  if (next.kind === "TIMEOUT") continue;
  if (next.kind === "CLOSED") break;
  envelope = decodeAndValidate(next.json);
  routeToPersistenceAndSubscribers(envelope);
}

// SSE 适配：cursor / 补读策略由宿主定义
writeSse({
  id: hostCursorFor(envelope),
  data: JSON.stringify(envelope)
});
// 浏览器 onmessage → 解析 envelope → reducer → UI

SSE 接入边界与现有示例

TRANSPORT DETAILS

帧保持完整

id: <host-cursor>
data: {完整 Runtime envelope}

保留 schema、type、实例 / 会话身份、序号与 payload。SSE 帧名不承担消息角色语义。

连通与对账分开

心跳维持连接可见性。Last-Event-ID 搭配宿主保留记录实现补读；缺口超出保留范围时，以快照重新建立基线。

副作用命令的去重与恢复，由业务协议另外保证。

已有 Studio 示例：支持 since / Last-Event-ID、完整 JSON data 与 15 秒心跳。使用其进程内事件日志和 event_seq 补读，范围限当前实例的保留记录；跨进程持久重放需要宿主扩展。

集成收益

公共 envelope 可供 UI、审计和存储复用。
审批等待与事件消费解耦。
每次 Call、命令受理与执行事实可以关联。

宿主需要落实

访问范围过滤、游标与补读保留。
首次订阅窗口与断线重连对账。
慢客户端隔离、队列监控与有限诊断载荷。
